Architecture, security, backup and monitoring

Load balancing

  • One server PC; up to 4 web workers (one per core) share the port, requests handed out in turn.
  • A worker that stops is restarted automatically; reminders and backups run in exactly one worker.
  • Logins are tokens checked against the database, so any worker serves any user.

Security

  • One login session per User ID; 30-minute idle timeout; administrators can end sessions.
  • Account locks for 15 minutes after 5 wrong passwords (Audit Log: LOGIN_LOCKED).
  • Request limit per PC as a guard against runaway scripts; uploads Excel only, 5 MB.
  • Optional HTTPS with a certificate from IT.
  • Dependency audit: server and the screens' runtime packages have no known vulnerabilities (one server fix and a React Router upgrade applied).

Backups

  • Nightly at 01:30, compressed, read back to verify before it counts.
  • Keeps 14 daily and 12 monthly copies; "Back up now" on System Health.
  • Restore script restores into a new database first, never over live data.
  • Copy the backup folder off the server PC (network share) for disk-failure protection.

Monitoring — Administration › System Health

  • Workers running and restarts, memory, wait time; request counts, errors and slow requests per screen.
  • Database size, ping, memory hit rate, connections, largest tables, queries over 5 seconds.
  • Logged-in users, last backup and free disk space; monthly logs of slow requests and errors.

Endurance, recovery and backup

20-minute endurance and recovery Passed

20 users at a realistic pace (a screen every 3 seconds) on the 10-year volume, with a full-year schedule run and a 1,000-row upload, and one web worker force-stopped at minute 8.

  • 7,255 screens and 24,108 requests, no errors.
  • Typical screen 67 ms; 95% under 1.0 s. Minute by minute the 95% figure stayed between 0.56 s and 1.6 s, with no slowdown over time.
  • The stopped worker was replaced automatically (System Health showed 1 restart); users saw no errors.
  • Worker memory rose and fell between about 80 and 610 MB as Node.js cleared memory, ending at 170–390 MB: no steady growth.

Backup and restore at the 10-year volume Passed

  • Backup of the 455 MB database (16.7 lakh schedule lines): 4 seconds, 13.8 MB compressed file, read back and verified (26 tables).
  • Restore into a new database: 54 seconds.
  • Every record count matched the original: 4,200 SD records, 18,842 SD transactions, 4,200 Rent Codes, 16,74,750 schedule lines, 60 users.
